Issue #1387 (Eigenbau, Owner go 2026-11-15). Measured 2026-11-15 on a store built
fresh from this repository (`import-all --from-repo`, Scryfall oracle bulk as the
card catalog; build log: pool 927, corpus decks 3,004). All figures below are

## 1. Step 0 — the semantics the repository itself defines

**Inclusion** (`src/commander_lab/studio/signals.py`): a commander file row stores
`value = num_decks / potential_decks` (`_share`, lines 240–244; `_commander_rows`,
lines 307–315) under the signal `edhrec_commander_inclusion`, with
numerator = `num_decks` and denominator = `potential_decks` as published
(`_deck_counts`, lines 288–304). Bracket files store the same figure under
`edhrec_bracket_inclusion:<variant>` with variant ∈ {core, upgraded, optimized,
cedh}; the EDHREC files themselves number the variants (bracket column: core = 2,
upgraded = 3, optimized = 4, cedh = 5 — counted in
`data/research/edhrec_20261115/commander_bracket_signals_*.csv`).

**Synergy** is stored as published, without counts (`_commander_rows`, lines
316–326): EDHREC's figure against EDHREC's color-identity population. The
repository defines no corpus synergy, and a single-commander local corpus has no
distinct color-identity baseline population — so **no synergy is filled**
(section 5).

**potential_decks** is EDHREC's published denominator and varies per card
(commander page: 1,241–9,816; release-window and population effects). The
repository's own denominator for counted data is the universe size
(`universe_decks` of a counted deck-list file): constant per universe. The fill
therefore carries `potential_decks := universe_decks` of the canonical corpus —
the only denominator definition the repository has for counted rows.

**Provenance** is carried twice: by the signal name and by `card_signal.source_id`
→ `source.title` (schema: `src/commander_lab/studio/store.py`, lines 399–407).
EDHREC rows live under `edhrec_*` signal names. A corpus-measured row must never
land there, for two repo-verified reasons:

1. A file in `commander_card_signals` shape is stored as
   `edhrec_commander_inclusion`/`edhrec_commander_synergy` — indistinguishable
   from EDHREC values for every consumer (e.g. `strength_view.card_signal_values`).
2. The import replaces per (commander, signal) pair (`_store_rows`, lines
   781–820): importing such a fill file after the EDHREC snapshot would delete
   the genuine EDHREC rows of the commander and replace them with corpus values
   under the EDHREC name.

The repository already has the structure for counted local rows: the deck-list
universe (`signals._import_decklists`, lines 882–978). A file
`<slug>_decklist_inclusion_<date>.csv` with columns `card_name, source, bracket,
decks_with_card, universe_decks` is stored as `decklist_universe:<source>:<bracket>`
(value the share, numerator/denominator the counts), its source row titled
`<file>#<snapshot>`, and consumers treat it as a complete count: a pool card
without a row is a counted zero, not unknown (`strength_view.signal_coverage`;
`universe_choice.counted_universes`, lines 95–130). The commander check of the
import (the commander's own card in every deck of the universe) holds by
construction for the commander's own corpus.

**Step-0 verdict: the fill fits the existing structures with clean provenance
separation — no consumer or logic change is needed.** The tier list's own counted
spread is unaffected: it is computed from the store decks via
`universe_choice.local_spec`, not from stored decklist universes (a counted
universe is only picked when the local lists fall below the minimum universe;
the local corpus counts 2,823).

## 2. Step 1 — cross-check first: corpus measurement vs. the EDHREC rows that exist

Method: per card, corpus inclusion = decks of the canonical corpus
(`universe.resolve_universe` over `universe_choice.local_spec`: 2,823 decks,
bound to exactly this commander, deduplicated by fingerprint) whose counted
sections (`store.COUNTED_SECTIONS` = main, mainboard, commander, companion,
`store.py` line 23) name the card with quantity > 0 — against the EDHREC
inclusion of `data/research/edhrec_20261115/commander_card_signals.csv`
(num_decks / potential_decks as published). Name resolution via the Scryfall
oracle catalog, with the front-face rule for two-part names (two EDHREC names
are front faces: Bala Ged Recovery, Growing Rites of Itlimoc).

Result over all **242** commander-page cards (no unmatched name, **no card
without a corpus hit**):

| figure | value |
|---|---|
| Spearman ρ, inclusion vs. inclusion | **0.9715** |
| Spearman ρ, EDHREC num_decks vs. corpus decks | **0.9800** |
| median \|Δ inclusion\| | **0.0168** |
| mean Δ inclusion | +0.0004 |
| cards within \|Δ\| ≤ 0.02 / ≤ 0.05 / ≤ 0.10 | 140 / 235 / 241 of 242 |

Largest deviations, with their mechanics:

- **Flickering Hound** (EDHREC 0.130 = 164/1,265; corpus 0.024 = 69/2,823;
  Δ −0.105) and **Pia, Aether Ascetic** (0.125 = 160/1,285; corpus 0.025 =
  70/2,823; Δ −0.100): the two largest. Both are new cards from EDHREC's
  "New Cards" section — EDHREC's denominator is a small recent window
  (1,265/1,285), the corpus denominator is the full stock of 2,823, and the
  corpus harvest only partly reflects the new cards' uptake. A denominator/
  window effect, not a counting error (both cards are counted, 69 and 70 decks).
- **Tatyova, Benthic Druid** (−0.063), **Cultivate** (−0.056), **Scute Swarm**
  (−0.053), **Avenger of Zendikar** (−0.052), **Kodama's Reach** (−0.052),
  **Beast Within** (−0.049): EDHREC higher. The corpus is bracket-heavy
  (brackets 4+5 = 1,158 of 2,823 decks, 41 %); popular casual/midrange cards
  are relatively more frequent in EDHREC's all-bracket population.
- **Temple Garden** (+0.046), **Hallowed Fountain** (+0.046), **Ranger-Captain
  of Eos** (+0.045): corpus higher — complete fetch/shock suites and competitive
  staples in the curated corpus, against EDHREC's broader population that
  includes budget lists.

Bracket cross-check (same counting, from the generated file of section 3,
against the four EDHREC bracket files): core (n = 208, corpus denominator 647)
ρ = 0.9912; upgraded (n = 230, 959) ρ = 0.9908; optimized (n = 247, 891)
ρ = 0.9868; cedh (n = 222, 267) ρ = 0.9658. (Values as recomputed from the
committed files in the independent review of this change; an earlier draft
of this section carried slightly lower figures from the live-store count.)

**Gate reading:** the corpus measurement reproduces EDHREC's ordering
(ρ ≈ 0.97–0.99) and, apart from the explained window/population effects, its
levels (median |Δ| under 0.02, no level bias). It measures the same quantity
over a different, local population — which is exactly what the fill is supposed
to be, under its own provenance.

## 3. Step 2 — the fill

Dataset: `data/research/corpus_fill_20261115/` (README there carries method and
regeneration), generated by `scripts/build_corpus_fill.py` from the fresh store.
One counted deck-list file, six universes, all `source = corpus`:

| universe (stored signal) | denominator | cards with a row |
|---|---|---|
| `decklist_universe:corpus:1-5` | 2,823 | 9,043 |
| `decklist_universe:corpus:1` | 66 | 2,298 |
| `decklist_universe:corpus:2` | 647 | 6,635 |
| `decklist_universe:corpus:3` | 959 | 5,548 |
| `decklist_universe:corpus:4` | 891 | 3,980 |
| `decklist_universe:corpus:5` | 267 | 1,347 |

28,851 rows in total. Bracket denominators do not sum to 2,823 (they sum to
2,830): seven duplicate twins carry different stated brackets, and a cohort
resolution — the way `corpus_signals.count_corpus` counts its cohorts — keeps a
twin the whole-corpus resolution deduplicates into another cohort. Cohorts are
never added (AGENTS.md §1); each universe stands alone, as the mechanism intends.

**Fill effect, with the exact sets.** The pool (`queries.legal_pool`, lines
13–32 of `queries.py`) counts 927 cards including the commander, 926 without it.
The ranked pool of the index (pool cards with a `rubric_h_mean` row) counts 922;
68 of them carry an EDHREC commander row, so **854 ranked pool cards have no
EDHREC commander row** — the figure of the issue, reproduced exactly. Of those
854, the fill gives **496 a counted row** (present in at least one canonical
deck) and **358 a counted zero** (a true 0 of 2,823 — the decklist semantics:
no row in a complete count). Pool-wide without the commander: 855 cards without
an EDHREC row → 497 with a corpus row, 358 counted zeros. (The one-card
difference between the two readings is an unranked pool card with corpus hits.)

One import notice, no action: 167 stored rows across the six universes (68 in
the whole-corpus universe) carry listed names that match no catalog card —
token names (Food, Beast, Copy, Saproling, Clue, …) that deck lists carry in
their main section. The 2026-11-12 counted file lists the same names; the
import keeps every row (the notice is informational, nothing is dropped).

## 5. Deliberately not filled

- **Synergy** — no repo-defined corpus figure exists (section 1); inventing one
  against a mixed baseline would be a modeled figure under a measured name.
- **Rows under `edhrec_bracket_inclusion:<variant>`** — those signals are
  EDHREC page figures; writing corpus counts there would break the provenance
  rule of section 1 (and the replace semantics would endanger the genuine
  rows). The bracket information of the fill lives in its own universes
  `corpus:1` … `corpus:5`, in the same bracket taxonomy EDHREC's files use
  (core = 2, upgraded = 3, optimized = 4, cedh = 5; bracket 1 has no EDHREC
  commander-page variant in `BRACKET_VARIANTS`).
- **Cards of other commanders** — the corpus is this commander's; nothing here
  states anything about another commander's decks.
