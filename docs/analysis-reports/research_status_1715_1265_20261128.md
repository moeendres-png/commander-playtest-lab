## #1715: trigger_order ties and frame divergence between JVM runs

The issue asked three questions.

**(1) Where does the input order of tied triggers come from?**
`CODE_DERIVED`, and it has two parts.
- **Fork part.** XMage iterates combat state keyed by random per-JVM UUIDs (the `HashMap<UUID, …>`
  in `CombatGroup`, named in `trigger_order_4p_1715_20261127.md` §"Abgrenzung"). The order in which
  simultaneous combat triggers reach `chooseTriggeredAbility` therefore changes from JVM to JVM.
- **Bridge part.** `XmageFullGamePlayer.chooseTriggeredAbility` sorts by label, then by the source's
  zone-change counter. It has no key that separates copies of the same ability from the same source.
  `abilityOptionId` is built from `sourceId` and `originalId` only. So the five `Thicket Basilisk`
  triggers of one multi-block get one and the same `option_id`, which was directly observed
  (`trigger_order_seed123_multiblock_1715_20261127.md` §2.3, frame 2485). The `byId` map then keeps
  only the last of them. The pilot cannot tell the copies apart, and which blocking creature's
  trigger goes first depends on the fork's UUID order.

**(2) Do such divergences reach the 4-seat reference set?**
`DIRECTLY_VERIFIED` as local Owner-PC measurements (`SIMULATED_RESULT`, no gate or CI credit),
from PR #1886 and PR #1862:
- On the random 4-seat table A4: 0 of 44 pairwise run comparisons diverged.
- Seed 123 is identical 8 of 8 times on jar `b1841482`, after the `Zone.EXILED` fix of #1802.
- On a table built to force multi-blocks: 20 of 20 runs gave different frame digests, and 12 of 20
  semantic hashes were distinct.

The gate reference set itself (the real pod, seeds 1 to 36) was not measured: `UNKNOWN`. The
random A4 table showed no divergence. The forced case is real, though.

**(3) Should the semantic hash capture state divergence?**
**Recommendation: no change.** A `NEUTRAL` bridge change must keep both the semantic transcript
hash and the normalized frame digest of every game identical (`AGENTS.md` §10). The frame digest
caught every divergence in the measurements above, including the ones the semantic hash missed
(frame 3141). Changing the hash definition would also cut the comparability of every past gate
run. A `NEUTRAL` gate PR may not change that code in any case.

**Next steps**

1. **Bridge, Lead decision, own package.** Give every trigger option a unique id, for example
   `sourceId`, `originalId` and the ability's own id, or an occurrence index after the stable sort.
   The fix includes a test that fails on the colliding ids. This is a `BEHAVIOUR` change under the
   Studio bridge gate. It does not make the order identical across JVMs, but every copy becomes
   addressable.
2. **Fork, Owner-only.** Replace the UUID-keyed iteration in `CombatGroup` with a deterministic
   order. This belongs in the bundle with the Master Chef and Menace fixes (#1093, #1628), which the
   Owner decides on (§8).

too few to say anything about strength.
