## Directly verified external facts

### OpenCode Go / Muse Spark 1.3 Contributor

Official OpenCode Go documentation (checked 2026-09-13):
`https://opencode.ai/docs/go/`

The service asks coding-agent clients to send a stable `x-opencode-session` value for
each conversation so routing and prompt caching can be optimized.

Pinned OpenCode `1.18.30` directly confirms the client-side implementation:
`packages/opencode/src/session/llm/request.ts` emits
`x-opencode-session: input.sessionID` for provider IDs beginning with `opencode`,
including `opencode-go`. Thus one stable OpenCode session directly supplies the Go
session-routing/cache-affinity key. This does **not** prove a cache hit for any particular
request; exported session metrics remain the authority for actual cache behavior.

Current listed Muse Spark 1.3 Contributor rates are per 1M tokens:

- input: `$0.10`
- output: `$0.20`
- cached read: `$0.002`
- cached write: not separately charged/listed
- monthly usage limit shown by Go: `$60`

Therefore a stable cached prefix is economically much cheaper than repeatedly creating
unique uncached input. This does **not** prove every prefix is cached; exported session
metrics remain the authority for actual cache behavior.

### Skills

Official OpenCode skills documentation states that permitted skills are advertised to
the model by ID/name/description; the full `SKILL.md` body is loaded only when the agent
calls the `skill` tool. This is the correct home for task-specific procedure that does
not need to occupy every turn's base context.

### Commands

Official OpenCode commands documentation supports project-local `.opencode/commands/*.md`
prompt templates, including shell-output interpolation. A command can therefore inject a
small deterministic, local context capsule instead of requiring a human to paste a large
workstream prompt.

## Adjudicated optimization strategy

The first optimization target is **dynamic context**, not aggressive removal of stable
critical governance.

Priority order:

1. Replace pasted multi-thousand-token workstream prompts with one tiny reusable TUI
   command that derives a compact execution capsule from authoritative local state.
2. Bound noisy tool/test output before it enters model context; retain full-output access
   for diagnosis.
3. Reuse the same OpenCode session for a workstream when safely possible; never use
   ambiguous `--continue` in a way that can target another live session.
4. Load detailed procedures as skills only when needed.
5. Remove only demonstrably redundant always-on instruction duplication. Do not weaken
   Rules Authority, evidence semantics, privacy, fail-closed behavior, source truth,
   ownership, or completion semantics for token savings.
6. Enable pruning of old tool outputs at compaction if the pinned CLI semantics are
   verified by tests. Do not introduce aggressive compaction thresholds without evidence.
7. Measure real sessions with exported OpenCode metrics. Never estimate token savings and
   label them as measured.

## Target operator experience

For a workstream whose contract/state has already been prepared by the Coordinator, the
human should eventually need only:

1. launch the validated Foundry session; and
2. type a short command such as `/work`.

The command should inject a small derived capsule containing only the fields needed to
start or resume execution (identity/source lock, objective, status/validated head,
exact-next-action, gates needed for that action, and concise Git state). The full state,
contract, evidence and skills remain available on demand.

This preserves quality because the authoritative data is still present; it changes how
much of it is eagerly serialized into every new prompt.
